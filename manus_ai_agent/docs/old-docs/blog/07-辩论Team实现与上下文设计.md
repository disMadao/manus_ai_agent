# 辩论 Team 实现与上下文设计

本文整理当前仓库里 **华语辩论 MVP** 的工程实现：赛段流程、单场内的「记忆」如何工作、辩手之间如何传递信息，以及与《06-辩论系统设计》的关系。代码主路径：`src/main/java/com/manus/aiagent/debate/`。

---

## 1. 设计目标（MVP 边界）

- **赛制**：硬编码状态机，按固定顺序跑完一场（准备 → 双方一辩 → 攻辩 → 自由辩 → 双方四辩总结）。
- **无真实计时**：用 **字符/字数上限** 约束单次发言长度；自由辩用「队内总预算 + 每轮上限 + 最大回合」结束。
- **无辩论专用持久化库**：不落用户表、不建 `debate_messages`；单场内容写 **`workspace/debate/{debateId}/`** 文本文件，便于人读与排错。
- **模型调用**：辩手统一走 **`LiteAgent` + DashScope `ChatClient`**（与主应用同一 `dashScopeChatModel` Bean），**未**默认开启 OpenFriend 里的 `enableThinking` 链路；若需「深度思考」需在实现上单独挂 `DashScopeChatOptions`。

---

## 2. 组件一览

| 类型 | 类 / 文件 | 职责 |
|------|-----------|------|
| 状态机 | `DebatePhase` | 枚举阶段与 `next()` 顺序 |
| 辩手 | `DebaterAgent` | 封装 `team` / `role`；`pro`/`con` 对应不同 **system** 与 user 中的角色任务；`speak(topic, context, maxChars)` 调模型 |
| 共享黑板 | `DebateFlowContext` | 单场内存中累积：核稿、立论、攻辩实录、自由辩逐行 |
| 协调器 | `DebateCoordinator` | `@Component`，驱动阶段、拼上下文、写文件 |
| 集成测试 | `DebateMinimalTestApplication`（test） | 只扫 `debate` 包 + 注入 `LiteAgent`，避免全量应用强依赖 PostgreSQL |

## 3. 整场流程（状态机）

```mermaid
flowchart LR
  P[准备 PREPARATION] --> A[正方一辩 PRO_OPENING]
  A --> B[反方一辩 CON_OPENING]
  B --> C[攻辩 CROSS_EXAM]
  C --> D[自由辩 FREE_DEBATE]
  D --> E[总结 CONCLUDING]
  E --> X[结束 END]
```

- **准备**：正反两队 **各跑一遍** `teamPreparation`，互不读对方准备稿（直到立论及之后才通过「赛场上下文」看到对方材料）。
- **立论**：正方一辩先发言，反方一辩后发言，反方提示词中显式包含 **正方立论全文**。
- **攻辩**：固定 4 轮，二辩问、三辩答（轮次在代码里交替攻守方）。
- **自由辩**：正反交替；每轮可见「核稿 + 立论 + 攻辩摘要 + 已发言自由辩」；每队有总「字数预算」（按汉字计数扣减），并设最大回合上限。
- **总结**：**反方四辩先**，**正方四辩后**；正方上下文额外包含 **反方四辩总结全文**。

## 4. 「记忆」到底是什么：没有 Agent 私有会话栈

### 4.1 核心结论

- **`DebaterAgent` 不保存多轮对话历史**。每次 `speak` 都是 **一次独立的 HTTP/模型调用**。
-单场内的「赛场记忆」= **`DebateFlowContext`（共享黑板）** + **协调器在当次调用前拼好的 `context` 字符串**。
- **不是**给每个辩手建向量库 / 会话表；进程结束，黑板即丢。这与「不要持久化辩论记忆」一致；若要做跨场次复盘，再另开存储即可。

### 4.2 `DebateFlowContext` 里有什么| 字段 | 含义 |
|------|------|
| `proTeamBrief` / `conTeamBrief` | 各队准备阶段产出的《队内核稿》正文（写入 flow，供后续阶段注入） |
| `proOpening` / `conOpening` | 双方一辩立论全文 |
| `crossExam` | 攻辩逐轮追加（问/答） |
| `freeDebate` | 自由辩每一行发言按时间追加 |

对外通过方法拼出 **带长度上限** 的文本，例如 `prepAndOpeningsForCross`、`freeDebateContextSoFar`、`fullDebateForConclusion`；超长时 **截断并附提示**，避免爆 token。

## 5. 各阶段：谁发言、上下文里装什么

下列「上下文」均进入 **`DebaterAgent` 的 user 提示词**（与辩题、正反角色任务、写作要求一起）。**System** 侧：公共辩论规则 + 正方「支持辩题」/ 反方「反对辩题」；与辩题具体句式无关，不在代码中拆「A是 B / A 不是 B」。

### 5.1 准备阶段（队内）

对 **每一队内部**（与对方队无消息通道）：

1. **独立思考**：四名辩手依次发言，提示词要求 **不引用队友**；上下文仅为辩题 + 任务。
2. **队内交流**：在「全队思考摘要」上逐人追加回应，**上下文随轮次变长**（队友已发言会进入后续轮次的 `context`）。
3. **轻量 research**：默认由 **二辩** 产检索问题；协调器可选调用 `WebSearchTool`（每队最多 2 条有效检索，可配置 key）；摘录写入队日志。
4. **队内核稿**：默认由 **一辩** 根据整份队日志写《队内核稿》；返回的 `brief` 写入 `DebateFlowContext`，并完整落盘 `*_team_prep.txt`。

**通信规则（队内）**：信息载体是 **协调器内存中的 `teamLog` 字符串** 与 **写文件**；没有「辩手 Agent 之间的 socket」，只有「上一轮模型输出作为下一轮提示词的一部分」。

### 5.2 立论阶段（队间首次交锋）

| 角色 | 注入的关键前文 |
|------|----------------|
| 正方一辩 | **正方《队内核稿》** + 任务：必须承接核稿框架 |
| 反方一辩 | **反方《队内核稿》** + **正方一辩立论全文** + 任务：至少点名对方一处具体论断 |

### 5.3 攻辩阶段

每一轮 **提问方** 与 **回答方** 共用同一块「赛场底板」拼接：

- **赛前双方核稿 + 双方一辩立论**（`prepAndOpeningsForCross`，有总字符上限）
- **截至上一轮的攻辩摘要**（`crossSoFarTrimmed`）

提问任务：须点名要攻击的对方论点；回答任务：先接问题，可引用己方立论/核稿。

每轮结束后 **`flow.appendCrossRound`**，保证后续轮次能看到本轮。

### 5.4 自由辩阶段

每轮发言前：`freeDebateContextSoFar`提供：

- 核稿 + 立论（中间层有内部截断上限）
- 攻辩实录摘要
- **自由辩已发言全文（按行追加）**

发言后把本行 `appendFreeLine` 进 flow，下一轮对手即可看到。

**预算规则**：每队 `FREE_TEAM_BUDGET`，每轮最多 `FREE_PER_TURN`；实际扣减按 **汉字数**（无汉字时退化为字符串长度）；并受 `MAX_FREE_ROUNDS` 限制。

### 5.5 四辩总结

- **反方四辩**：`fullDebateForConclusion`（全场纪要，有总上限）+ 总结任务（须引用或概括至少一处对方表述）。
- **正方四辩**：在同样全场纪要之上，**追加反方四辩总结实录**，再总结与回应。

## 6. Agent 之间「通信」规则（归纳）

| 通道 | 谁与谁 | 机制 |
|------|--------|------|
| 队内 | 同队 1–4 辩 | 准备阶段：前序发言文本拼进后续 `context`；核稿由一辩汇总全队日志 |
| 队间 | 正 vs 反 | **仅通过协调器**把「已发生的立论/攻辩/自由辩」写入共享黑板，再在当次 `speak` 注入；**无**辩手实例间直接调用 |
| 人 / 运维 | 开发者 | 读 `workspace/debate/...` 下带序号文件（如 `01_…`～`09_…`）与 `09_transcript.txt` |

本质上：**通信 = 协调器维护的有序公共缓冲区 + 提示词工程**，不是多 Agent 消息总线。

---

## 7. 字数、截断与可调参数

实现里用 **字符长度** 做 `maxChars` 与输出截断（`DebaterAgent.truncate`）；自由辩 **扣预算** 优先数 **CJK 汉字**。

主要常量集中在 **`DebateCoordinator`**（准备/立论/攻辩/自由辩/总结上限，以及注入上下文窗口 `CROSS_BASE_CTX`、`FREE_CTX`、`CONCLUSION_CTX` 等）。当前数值曾在「过短」反馈后 **整体放宽过一版**，后续仍可只改常量、不改状态机。

---

## 8. 输出目录怎么读

建议顺序：按文件名 **`01_`～`09_` 字典序** 即可对齐赛段：`01` 正方准备 → `02` 反方准备 → `03`/`04` 立论 → `05` 攻辩 → `06` 自由辩 → `07`/`08` 四辩总结（先反后正）→ **`09_transcript.txt`** 全场日志导览。也可先看 `09` 再回读 `01`～`08`。

## 10. 测试与运行注意

- **全量** `AiAgentApplication` 集成测试会拉起 PostgreSQL 等依赖；辩论集成测试使用 **`DebateMinimalTestApplication`** + `local` + `debate-test` profile（内存 H2 占位数据源），见 `src/test/java/com/manus/aiagent/debate/`。
- **正式主启动类未改为辩论专用**；`DebateCoordinator` 作为 Spring Bean 存在于全量应用中，但需业务代码显式调用 `runDebate` 才会执行。

## 11. 已知局限与可演进方向

- **模型质量**：依赖提示词与字数；未默认开 DashScope `enableThinking`，观感「浅」时需从 **options + 提示结构** 下手。
- **上下文截断**：极长场次下早期内容可能被截断，需分层摘要或「关键论点缓存」才能进一步逼近真人辩论的信息量。
- **角色分工**：攻辩固定二、三辩；准备阶段检索默认二辩出题、一辩写核稿——若要可配置，可抽策略接口。
- **REST / 流式**：当前 MVP 以文件与测试入口为主；若要对前端暴露，可在不改 `main` 的前提下增加 Controller。
